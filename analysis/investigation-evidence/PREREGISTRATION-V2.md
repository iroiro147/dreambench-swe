# Frozen Pre-registration V2 -- DreamBench-SWE scaled confirmatory fold

Status: **FROZEN**.

This document governs the DreamBench-SWE v2 scaled confirmatory fold. It is a
mechanical merge of the v2 draft with the binding scale-freeze decisions. Where
any prior planning note, draft, or support document conflicts with this file,
the freeze decisions govern and this file records their operational form.

## 0. Scope and binding rule

This document governs the next confirmatory DreamBench-SWE / DreamForge fold. It
does not rewrite the already reported v1 fold. It defines the scaled trap set,
validity gates, authoring controls, condition matrix, primary statistical
analysis, falsifiers, second wake-model transfer fold, and go/no-go criteria for
the v2 scaled result.

Definitions:

- **Trap** means one multi-session sequence whose S3 task is the scored memory
  trap. In the primary analysis, a trap is the statistical cluster.
- **Cell** means one `(trap, seed, condition)` S3 outcome.
- **Seed schedule** means seeds `1`, `2`, and `3` unless explicitly stated
  otherwise.
- **Primary outcome** is S3 executable pass/fail after the validity gate.
- **Primary paired unit** is the trap cluster. The three seeds are repeated
  observations within a trap, not independent benchmark items.
- **Primary wake-model fold** is the `gpt-5.5` wake-agent fold.
- **Second wake-model fold** is a separate transfer check, not a pooled
  extension of the primary fold.
- **Construct label** means one of `C1` through `C10` in Section 2.2.
- **Family label** means the legacy DreamBench-SWE family label. Family is
  recorded separately from construct and cannot override construct quotas.

Hard binding rule:

```text
No new V2 trap may be authored after looking at any V2 performance result.
```

The only result-like information allowed before final trap freeze is the
pre-declared validity-gate verdict for candidate admission: B0 S3 fail,
reference solution pass, oracle hidden, CSPRNG-secret compliance,
no-single-event or construct-specific gate where applicable, clean-start flag
where applicable, and manifest/schema checks. Once any memory-bearing condition
has produced an S3 result on any v2 candidate trap, trap authoring is closed
permanently for this fold.

## 1. Honest causal history ledger

The scaled fold is designed after the v1 fold, after mock reviews, after the
8-trap synth pilot, and after the scale-freeze review. The paper and any release
note using v2 must disclose this history.

Known v1 facts before v2 design:

- The current v1 benchmark has 22 traps x 3 seeds = 66 S3 cells for complete
  conditions.
- The v1 appendix classifies 18 of 22 traps as recall-verbatim and 4 as
  synthesis/apply. This makes B5, the verbatim event-memory baseline,
  structurally strong.
- DF-hybrid led B5 numerically in v1 but did not significantly beat it:
  `52/66 = 0.788` vs `48/66 = 0.727`, exact McNemar `b=12, c=8, p=0.503`,
  Holm `p=1.0`.
- The positive v1 typed-only-vs-B3 result survived the trap-clustered exact test
  but not all conservative sensitivity variants; seed concentration remained a
  weakness.
- The v1 falsifier set had important failures, especially low
  `UsefulMemoryPrecision` and excessive seed spread.
- Mock reviews flagged the benchmark as too small, too recall-verbatim-heavy,
  too dependent on pooled seed-trap inference, and too tied to one wake model.

Corrected synth-pilot citation before v2 freeze:

- The synth pilot is cited only as a pre-registered directional slice and is
  never pooled into the v2 confirmatory sample.
- The corrected denominator is `n=24` S3 cells: 8 synth traps x 3 seeds.
- Corrected S3 pass rates are:

| Condition | Synth-pilot S3 pass rate |
|---|---:|
| B0 | 0.000 |
| B1 | 0.000 |
| B5-MEM0 | 0.000 |
| B3 | 0.125 |
| DF-typed-only | 0.167 |
| B5 | 0.250 |
| DF-hybrid | 0.250 |
| DF-raw-only | 0.292 |

- Corrected synth-pilot warmup was `0.75-0.81`.
- Any earlier text that implied a different pilot count, denominator, or pooled
  interpretation is superseded by this correction.

Bias risks created by that knowledge:

- Authors could intentionally write traps that punish B5's verbatim strategy.
- Authors could write synthesis traps around operators where DF appeared strong.
- Authors could avoid families, constructs, or pathologies where DF failed in
  v1.
- Authors could overfit hidden literals, event structure, or distractor count to
  the known read limits of a condition.
- Authors could remove or rewrite traps after seeing early v2 outcomes.
- LLM-authored trap skeletons could encode model-family biases, templated
  structure, or inferable "random" tokens if secrets are not generated by the
  harness.

Mitigations:

- New traps are allocated by the construct quotas in this document, not by
  observed v1 per-trap DF/B5 outcomes.
- Every trap carries both a construct label (`C1` through `C10`) and a family
  label. Family names are not treated as construct names.
- New trap authoring must proceed from frozen templates that specify construct,
  family, required event structure, hidden oracle shape, labels, CSPRNG secret
  fields, and validity checks before any condition result is available.
- New trap authors may know the aggregate v1 and synth-pilot facts listed
  above, but should not consult the per-trap v1 outcome matrix while drafting
  individual v2 traps. If a maintainer must consult it for deduplication or
  naming, that access is logged.
- Candidate trap hashes, sequence ids, construct labels, family labels, oracle
  ids, CSPRNG secret manifests, authoring skeleton ids, template ids, and
  validation reports are frozen before the first memory-bearing v2 run.
- A trap can be rejected before the run only for a pre-declared validity-gate
  failure. It cannot be removed after outcome inspection because it is hard,
  easy, inconvenient, unfavorable, or embarrassing.
- If the primary clustered test is null, the null result is published. Pooled
  McNemar, construct slices, family slices, hygiene metrics, or the second
  wake-model fold cannot replace it as the headline.

## 2. Trap set

### 2.1 Target size and composition

The v2 target is **60 valid S3 traps**, each run on 3 seeds, for:

```text
60 traps x 3 seeds = 180 S3 cells per complete condition
```

The target composition is:

```text
22 v1 traps + 8 synth-pilot traps + approximately 30 new traps = 60 traps
```

Sixty valid traps is the confirmatory target. The target is chosen because the
primary test is clustered by trap, so adding seeds without adding traps does not
solve the main pseudo-replication concern. The scale also satisfies the
anti-hoarding quota in Section 2.3.

This target is not a promise that small effects will be detectable. Under the
primary clustered exact sign/permutation test, v2 is powered only for moderate
to large trap-level directional effects. Section 6 gives the arithmetic.

### 2.2 Construct inventory and target quota

The governing allocation unit is construct, not legacy family. The frozen
construct quota is:

| Construct | Construct name | Target n | Role in v2 |
|---|---|---:|---|
| C1 | Verbatim retention | 18 | v1 continuity and B5 calibration anchor |
| C2 | Retrieval precision under interference | 6 | anti-hoarding, executable precision under distractors |
| C3 | Staleness detection and supersession | 7 | anti-hoarding, stale suppression and multi-hop supersession |
| C4 | Update propagation / regression avoidance | 1 | probe for derived update propagation |
| C5 | Scope discipline | 6 | anti-hoarding, overgeneralization resistance |
| C6 | Contradiction handling / provenance conflict | 5 | anti-hoarding, authority and precedence under conflict |
| C7 | Cross-session synthesis / paraphrase-retention application | 7 | powered non-verbatim composition and paraphrase-retention control |
| C8 | Procedural / source-of-truth memory | 4 | generated-source workflow and procedural memory |
| C9 | Spurious-lesson rejection / disconfirmation | 4 | anti-hoarding, bad-memory rejection |
| C10 | Abstention / confabulation resistance | 2 | anti-hoarding probe, irrelevant-memory rejection |
| **Total** |  | **60** |  |

Quota arithmetic:

```text
18 + 6 + 7 + 1 + 6 + 5 + 7 + 4 + 4 + 2 = 60 traps
```

C1 recall-verbatim is capped at 24 traps total, including the 18 v1
recall-verbatim traps. The frozen target is 18 C1 traps. If validation forces
replacement or relabeling, C1 may not exceed 24 traps and may not exceed 40% of
the final valid set.

Each construct definition:

- **C1. Verbatim retention:** preserve a non-inferable exact token, format, or
  rule from one prior event and reproduce it when relevant. Storage of the
  single event is necessary and sufficient.
- **C2. Retrieval precision under interference:** find the one relevant stored
  fact among many stored facts within a fixed read-token budget. Retention is
  easy; selection is the skill.
- **C3. Staleness detection and supersession:** when a fact is superseded by a
  later event, use the new fact and do not use the old one, even when the old
  one is more salient. At least two C3 traps must defeat a simple
  newest-event heuristic.
- **C4. Update propagation / regression avoidance:** after a fact changes,
  derived usages must change consistently in a later location that was not
  directly patched by the superseding event.
- **C5. Scope discipline:** apply human feedback within its stated scope and
  refuse to apply it outside that scope.
- **C6. Contradiction handling / provenance conflict:** resolve conflicting
  sources by an established authority or precedence rule rather than by raw
  recency or arbitrary choice.
- **C7. Cross-session synthesis / paraphrase-retention application:** derive an
  answer from two or more events, or apply a paraphrased retained instruction,
  such that no single event contains the decisive S3 answer as a contiguous
  literal.
- **C8. Procedural / source-of-truth memory:** remember how the repo expects a
  change to be made, such as editing a generator rather than a generated
  artifact.
- **C9. Spurious-lesson rejection / disconfirmation:** reject an unsupported or
  later-disconfirmed lesson, even when a stored memory suggests a wrong causal
  story.
- **C10. Abstention / confabulation resistance:** recognize that no prior event
  bears on the current task and avoid fabricating benchmark-style tokens or
  importing irrelevant memories.

### 2.3 Anti-hoarding and recall-verbatim constraints

At least one third of the final valid set must come from anti-hoarding
constructs:

```text
>= 20 of 60 traps must be anti-hoarding traps
```

For this preregistration, the anti-hoarding constructs are C2, C3, C5, C6, C9,
and C10, plus any C7 trap explicitly labeled as paraphrase-retention where
byte-copying is insufficient and indiscriminate raw replay is not enough.

The frozen target anti-hoarding count from C2, C3, C5, C6, C9, and C10 alone is:

```text
C2 6 + C3 7 + C5 6 + C6 5 + C9 4 + C10 2 = 30 anti-hoarding traps
```

This exceeds the binding floor of 20 anti-hoarding traps. The excess is not a
separate headline claim; it is the planned construct balance.

Recall-verbatim constraints:

- C1 target: 18 traps.
- C1 maximum: 24 traps.
- C1 must not exceed 40% of the final valid set.
- The legacy `flaky-test` family label does not imply an anti-hoarding
  construct. In v1, all flaky-test traps audited as recall-verbatim and must be
  labeled C1 unless redesigned and revalidated under another construct.

### 2.5 Clean-start subset

At least 10 of the new traps must use clean-start S3:

```text
>= 10 new traps with clean_start_s3 == true
```

For clean-start traps, S3 intentionally does not inherit the S1/S2 production
tree. The S3 worktree starts from the frozen clean base for the fixture repo,
while the memory-bearing conditions still receive only the admissible memory
context from prior sessions. These traps separate memory failure from inherited
implementation-state failure.

Clean-start traps are not continuation failures. The run manifest and analyzer
must distinguish:

- ordinary continuation traps, where S2 starts from S1 and S3 starts from S2;
- clean-start S3 traps, where S3 starts from the clean base by design.

### 2.6 CSPRNG secret-injection protocol

CSPRNG secret injection is a binding authoring rule.

Authoring protocol:

1. The authoring LLM drafts only a trap skeleton with named placeholders for
   non-inferable tokens, ids, marker strings, format literals, and oracle
   literals.
2. The authoring LLM never invents a secret token, never selects a random-looking
   literal, and never writes the final hidden oracle literal by hand.
3. The harness generates all secret tokens with a cryptographic random source.
4. The harness substitutes generated secrets into:
   - injected memory events;
   - hidden oracle expectations;
   - reference solution material;
   - decisive-literal metadata;
   - any public prompt field where the event itself is supposed to reveal the
     token.
5. The sequence manifest records a secret manifest hash and generator-code hash,
   but not secret values beyond those intentionally present in public injected
   events.
6. The validator rejects any candidate whose decisive non-inferable secret was
   authored directly by an LLM or a human rather than injected by the harness.

This is the by-construction inferability defense. It is not optional, and it is
not replaceable by prose disclosure or post-hoc audit.

### 2.7 No-single-event and construct-specific gates

Every non-C1 trap must declare the mechanism by which verbatim replay is
insufficient:

- C2 breaks retrieval budget sufficiency under distractor interference.
- C3 makes a stale memory attractive and requires supersession or suppression.
- C4 requires applying an update rule to a derived location.
- C5 makes out-of-scope memory use harmful.
- C6 requires authority or provenance reasoning across conflicting events.
- C7 requires composition or paraphrased application; no single event contains
  the complete decisive answer.
- C8 requires procedural source-of-truth behavior, not only output recall.
- C9 makes a stored lesson actively wrong after disconfirmation.
- C10 requires abstaining from irrelevant memory use.

Required metadata for every non-C1 trap:

- `decisive_oracle_literals`, where the oracle has literal checks;
- `required_fact_ids`;
- `event_fact_map`;
- `insufficiency_mechanism`;
- `single_event_complete_answer`, expected `false` unless the construct-specific
  gate explains why the checked behavior is not literal-copy sufficient;
- commission checks, where the correct behavior must appear;
- omission checks, where the trap behavior must be absent.

The automated gate must verify:

- No normalized decisive oracle literal is a substring of any single injected
  event's `content`, except for C1 or for explicitly declared visible input
  literals that are not themselves sufficient.
- No single injected event covers all `required_fact_ids` for non-C1 traps.
- The S3 prompt does not reveal the decisive answer.
- The public repository state before S3 does not contain the decisive answer
  unless the trap is explicitly an apply/derive case where visible repo state
  contains one input and memory supplies another.
- The trap is passable in principle by any system that surfaces the needed facts.
  The design must not rely on B5 read-limit overflow, distractor-event stuffing,
  or a DreamForge-specific operator as the only viable path.

Rejected design target:

```text
"Make B5 fail."
```

B5 passing a non-C1 trap is an outcome, not an authoring defect. The goal is to
measure construct-specific memory behavior, not to engineer a DF win.

## 3. Authoring, admission, and audit protocol

### 3.1 Admission funnel

The v2 report must disclose the full admission funnel:

```text
N generated skeletons
-> N with CSPRNG secrets injected
-> N passing schema and manifest checks
-> N passing refsol/oracle checks
-> N passing B0/no-memory S3 failure
-> N passing leakage/canary checks
-> N passing no-single-event or construct-specific gates
-> N passing template-cap checks
-> N human-reviewed for construct labels
-> 60 admitted traps
```

For every rejected candidate, the manifest records the first failing gate and
whether the candidate was discarded, repaired before outcome inspection, or
reserved as a replacement candidate before freeze.

### 3.2 Template cap

No more than four admitted traps may share the same trap skeleton:

```text
<= 4 admitted traps per skeleton_id
```

The template cap is checked before final freeze. A skeleton is defined by the
structural event pattern, oracle pattern, task type, and fixture surface, not by
the exact token values. Renaming tokens or swapping fixture nouns does not create
a new skeleton.

### 3.3 Human audit protocol

Human audit is required before final trap freeze:

- 100% of admitted traps receive human review of construct labels.
- At least 30% of admitted traps receive deep audit for construct fit, realism,
  leakage risk, template duplication, and whether the stated insufficiency
  mechanism is actually load-bearing.
- Agreement is reported with raw agreement and Cohen's kappa where applicable.
- Disagreements are resolved before freeze.
- Traps with unresolved construct-label disagreement may remain in the benchmark
  only as benchmark traps; they are excluded from per-construct claims.

Human audit does not replace machine validation. Refsol pass, oracle hiddenness,
B0 failure, CSPRNG secret generation, no-single-event checks, continuation or
clean-start status, and contamination checks remain machine gates.

### 3.4 Author x solver interaction analysis

Every trap records `author_model`. The scaled report must analyze the
author-model x wake-model interaction across both backbones.

Required reporting:

- pass rates by `author_model`, `wake_model`, condition, and construct;
- the difference in `gpt-5.5` wake performance versus second-backbone wake
  performance, stratified by author model;
- a trap-clustered descriptive interaction estimate for whether traps authored
  by a model family are differentially easier for that same family as solver;
- a sensitivity table excluding traps authored by the same model family as the
  primary wake model, if such traps exist in sufficient number.

This analysis is secondary and cannot rescue or replace the primary clustered
comparison. It is a contamination and construct-validity check.

## 4. Validity gate and run-blocking harness fixes

### 4.1 Per-trap gate

Run the live trap validator:

```bash
python3 experiments/validate_trap.py \
  --sequence-records <candidate-sequence-records> \
  --seq <seq_id> \
  --live
```

A new trap is admissible only if the validation verdict has:

- `valid == true`;
- `b0_s3_failed == true`;
- `refsol_passes == true`;
- `oracle_hidden == true`;
- `csprng_secret_injected == true`;
- no public task leak of `oracle_cmd`, absolute oracle path, hidden tests, hidden
  labels, expected pass/fail, reference patches, future injected events, secret
  manifests, or benchmark result artifacts;
- the construct-specific gate passes;
- `clean_start_s3` is correctly represented in the manifest and validator.

For C7 traps, the no-single-event gate is required. For C3, C5, C6, C9, and C10,
the oracle must check both correct behavior and absence of the construct-specific
trap behavior.

### 4.2 Continuation and clean-start scoring gate

For ordinary continuation traps, each admitted sequence must preserve the
memory-trap continuation invariant:

```text
S2 starts from S1's scored production tree.
S3 starts from S2's scored production tree.
```

The run record must show:

- `started_from_previous_session == true` for S2 and S3;
- `previous_session_end_commit == start_commit` for S2 and S3;
- `forbidden_fresh_base_ref_used == false`;
- scoring applies only the production diff to a fresh scorer checkout;
- edits to tests, `.git`, import hooks, `conftest.py`, `pytest.ini`,
  `sitecustomize.py`, and `*.pth` are rejected before scoring.

For clean-start S3 traps, the run record must instead show:

- `clean_start_s3 == true`;
- S3 starts from the frozen clean base specified in the manifest;
- the analyzer does not count the intentional clean start as continuation
  invalidity;
- S1 and S2 records remain present and valid as memory-source sessions.

### 4.3 B0 headroom cap

Per-trap admission requires B0 to fail S3 in the live validator. The final scaled
run also has an aggregate B0 headroom cap:

```text
B0 S3 pass rate <= 0.40 preferred
B0 S3 pass rate <= 0.50 maximum acceptable
```

If final B0 S3 pass rate is greater than 0.40 but less than or equal to 0.50, the
benchmark may still be reported, but every benchmark-validity claim must carry a
difficulty caveat. If final B0 S3 pass rate is greater than 0.50, the scaled fold
cannot be claimed as a valid memory-trap benchmark, regardless of DF's result.

B0 warmup must not be the bottleneck:

```text
B0 S1+S2 warmup pass rate >= 0.80
```

If B0 fails warmups below this threshold, S3 failures cannot cleanly be
interpreted as memory failures.

## 6. Primary analysis and power

### 6.1 Outcome

The primary outcome is validity-gated S3 executable pass/fail for each
`(condition, seed, trap)` cell.

Warmup rates, hygiene metrics, cost, construct slices, family slices, and
authoring diagnostics are reported, but they do not replace the primary S3
analysis.

### 6.2 Primary clustered test

The primary inferential test is an exact trap-clustered sign/permutation test.
For each comparison `A` vs `B` and trap `t`, define:

```text
d_t =
  # paired valid seeds where A passes and B fails
  -
  # paired valid seeds where A fails and B passes
```

Tied paired seed cells contribute 0. The observed statistic is:

```text
D_obs = sum_t d_t
```

Under the null, the sign of each nonzero trap contribution is exchangeable. The
two-sided exact p-value is:

```text
p = Pr(|sum_t s_t * |d_t|| >= |D_obs|)
    over all sign assignments s_t in {-1, +1}
```

Zero-contribution traps are retained in descriptive counts but do not increase
the number of sign-flip states. The implementation may enumerate signs directly
or use exact dynamic programming; no normal approximation is used for the primary
p-value.

The primary paired unit is the trap. Seed-level cells are within-trap repeated
measurements.

### 6.3 Primary comparison family and correction

The primary S3 comparison family from the draft is fixed as six comparisons.
They are named `P1` through `P6` here to avoid collision with construct labels
`C1` through `C10`.

| ID | Comparison | Purpose |
|---|---|---|
| P1 | `DF-hybrid` vs `B5` | headline comparison against strongest v1 baseline |
| P2 | `DF-typed-only` vs `B5` | typed consolidation alone against verbatim memory |
| P3 | `DF-raw-only` vs `B5` | raw evidence retention against B5 |
| P4 | `DF-hybrid` vs `DF-raw-only` | incremental value of typed maintenance above raw evidence |
| P5 | `DF-hybrid` vs `DF-typed-only` | incremental value of raw evidence channel above typed-only |
| P6 | `DF-typed-only` vs `B3` | structured typed memory against reflection/vector anchor |

All six primary p-values are two-sided exact clustered p-values. Holm-Bonferroni
correction controls family-wise error at alpha `0.05` across P1-P6.

Allowed headline claims:

- `DF-hybrid > B5` requires P1 to have positive `D_obs` and Holm-adjusted
  clustered `p < 0.05`.
- If P1 is null, the paper must say the scaled fold does not establish
  `DF-hybrid > B5`, even if pooled McNemar, construct slices, family slices, or
  transfer analyses are significant.
- If P4 is null, the paper cannot claim typed maintenance adds task-success
  value beyond raw evidence retention.
- If P5 is null, the paper cannot claim raw evidence adds task-success value
  beyond typed-only consolidation.
- If P6 is significant but P1 is null, the paper may claim only the specific
  typed-vs-B3 result, with the B5 null stated beside it.

### 6.4 Missingness and exclusions

No imputation is allowed.

For each comparison:

- a paired seed cell is included only if both conditions have a validity-gated
  S3 outcome for that `(trap, seed)`;
- a trap with at least one paired valid seed contributes its available `d_t`;
- traps with no paired valid seeds for a comparison are excluded from that
  comparison and listed;
- a sensitivity table must report paired cells, contributing traps, and paired
  seeds per trap.

Confirmatory claim thresholds:

- P1 requires at least 54 traps with at least two paired valid seeds.
- P1 cell-level validity exclusions must be <=5% for each side. With 180 cells,
  this means no more than 9 excluded cells per side for P1.
- If exclusions are >5% for either side, P1 may be reported only as incomplete.
- If exclusions are condition-skewed, the missingness pattern is treated as a
  failure mode and cannot be silently ignored.

### 6.5 Secondary pooled McNemar and descriptive strata

Pooled exact McNemar is secondary and uses the seed-trap cell as the paired unit.
It is computed for the same P1-P6 family, with the same two-sided alternative
and Holm correction.

Pooled McNemar can support sensitivity language only. It cannot overturn a null
primary clustered P1.

Required sensitivity reports:

- per-seed exact McNemar for P1-P6, Holm-corrected within seed;
- trap-majority collapse for P1-P6, Holm-corrected;
- construct-slice outcomes for P1, descriptive only unless a future amendment
  freezes a separate construct-level inferential family before any run;
- family-slice outcomes for P1, descriptive only unless a future amendment
  freezes a separate family-level inferential family before any run;
- author-model x wake-model descriptive interaction table.

Per-construct strata are reported descriptively because n is small per stratum.
They constrain claims and falsifiers, but they do not replace the primary
clustered test.

### 6.6 Effect sizes

Every comparison table reports:

- clustered `D_obs`;
- cell-level `b`, `c`, and paired `n`;
- trap count and paired seed distribution;
- raw pass rates by condition;
- paired cell difference `(b-c)/paired_n`;
- trap-level sign balance;
- Holm-adjusted clustered p-value;
- secondary pooled McNemar p-value and Holm p-value.

Failure to reject is not equivalence. No equivalence or non-inferiority claim is
allowed unless a separate equivalence margin is frozen before the run.

### 6.7 Power and minimum detectable effect

The primary clustered test does not depend only on 180 pooled cells. It depends
on the number of traps with nonzero discordance and on how discordant seeds are
clustered within traps.

For intuition, if `k` nonzero traps each have equal weight, the clustered test
reduces to an exact sign test. If `b` of the `k` nonzero traps favor DF and
`c = k-b` favor B5, the two-sided p-value is:

```text
p = 2 * sum_{i=b..k} binom(k, i) / 2^k
```

for `b > k/2`.

Equal-weight rejection thresholds at alpha `0.05`, recomputed for a 60-trap,
180-cell design:

| Nonzero trap clusters `k` | Minimum DF-favoring split | Exact two-sided p | If one discordant seed per trap: discordant cell rate | Net cell margin | If all 3 seeds discordant in same direction: discordant cell rate | Net cell margin |
|---:|---:|---:|---:|---:|---:|---:|
| 20 | 15-5 | 0.041389 | 20/180 = 0.111 | 10/180 = 0.056 | 60/180 = 0.333 | 30/180 = 0.167 |
| 30 | 21-9 | 0.042774 | 30/180 = 0.167 | 12/180 = 0.067 | 90/180 = 0.500 | 36/180 = 0.200 |
| 40 | 27-13 | 0.038477 | 40/180 = 0.222 | 14/180 = 0.078 | 120/180 = 0.667 | 42/180 = 0.233 |
| 50 | 33-17 | 0.032839 | 50/180 = 0.278 | 16/180 = 0.089 | 150/180 = 0.833 | 48/180 = 0.267 |
| 60 | 39-21 | 0.027340 | 60/180 = 0.333 | 18/180 = 0.100 | 180/180 = 1.000 | 54/180 = 0.300 |

The 60-cluster arithmetic is:

```text
38-22 split: p = 0.051894, not below 0.05
39-21 split: p = 0.027340, below 0.05

If one discordant seed per trap:
  DF-only cells = 39
  B5-only cells = 21
  net margin = (39 - 21) / 180 = 18 / 180 = 0.100

If all three seeds are discordant in the same direction within each trap:
  DF-only cells = 39 * 3 = 117
  B5-only cells = 21 * 3 = 63
  net margin = (117 - 63) / 180 = 54 / 180 = 0.300
```

Approximate power under the equal-weight sign model:

| Nonzero clusters `k` | Rejection threshold | Power if true DF-favoring probability among nonzero clusters is 0.65 | Power at 0.70 | Power at 0.75 |
|---:|---:|---:|---:|---:|
| 20 | >=15/20 | 0.245 | 0.416 | 0.617 |
| 30 | >=21/30 | 0.358 | 0.589 | 0.803 |
| 40 | >=27/40 | 0.441 | 0.703 | 0.897 |
| 50 | >=33/50 | 0.506 | 0.782 | 0.945 |
| 60 | >=39/60 | 0.559 | 0.838 | 0.970 |

Therefore, 60 traps is a reasonable target for detecting a large, stable
trap-level DF advantage. It is not enough to guarantee detection of small
effects, sparse discordance, or effects concentrated in a small number of trap
templates. The actual primary p-value will be computed from the observed `d_t`
vector, not from this equal-weight approximation.

## 8. Falsifiers

Falsifiers constrain the causal story. They do not authorize hiding the result.
If a falsifier fails, the result still publishes with the corresponding claim
removed or narrowed.

### F1. B0 headroom

Pre-committed threshold:

```text
B0 S3 pass rate <= 0.40 preferred
B0 S3 pass rate <= 0.50 maximum acceptable
```

If `B0 > 0.50`, the benchmark does not force memory use strongly enough and the
scaled fold cannot support memory-trap claims.

### F2. UsefulMemoryPrecision, retained from v1

V1 failure: `UsefulMemoryPrecision` was too low under the primary judge, and the
cross-model rescore showed judge dependence while still leaving B5 stronger on
precision.

V2 threshold:

```text
DF-hybrid UsefulMemoryPrecision >= 0.45 under the primary scorer
and
DF-hybrid UsefulMemoryPrecision no more than 0.15 below B5
```

If a cross-model hygiene rescore is run, the same absolute and relative values
must be reported for both DF-hybrid and B5. The pass/fail interpretation is
primary-scorer based, but a cross-model reversal or much larger B5 advantage
must be disclosed.

### F3. Seed spread, retained from v1

V1 failure: seed spread exceeded the pre-registered stability target.

V2 threshold:

```text
DF-hybrid S3 pass-rate max(seed) - min(seed) <= 0.12 preferred
DF-hybrid S3 pass-rate max(seed) - min(seed) <= 0.16 maximum for a stability claim
```

With 60 traps, a 0.12 spread is at most 7 traps between best and worst seed
because `7/60 = 0.117` and `8/60 = 0.133`. A 0.16 spread is at most 9 traps
because `9/60 = 0.150` and `10/60 = 0.167`. A spread above 0.16 means the paper
may report aggregate rates but may not claim stable seed behavior. The same
spread is reported for B5, DF-typed-only, and DF-raw-only.

### F4. Regression and repeated-error hygiene

V2 thresholds:

```text
DF-hybrid RepeatedErrorRate <= B5 RepeatedErrorRate
DF-hybrid RepeatedErrorRate <= 0.15
DF-hybrid RegressionAfterUpdate <= 0.08
```

Justification: v1 showed a favorable repeated-error direction but a failed
regression-after-update target under the primary judge. V2 keeps both axes. The
RAU threshold is less brittle than the v1 `0.045` target but still requires that
raw retention plus typed maintenance not create a high regression burden.

### F5. Strict-hybrid recovery and contradiction-record handling

If `DF-strict-hybrid` is included, it must not reproduce the v1 strict inversion.
Threshold:

```text
DF-strict-hybrid S3 pass rate >= 0.60
and
DF-strict-hybrid S3 pass rate no more than 0.12 below DF-hybrid
```

If this fails, the paper cannot claim the contradiction-record/read-path fix is
general. It may still report DF-hybrid, but strict retrieval is a failed
configuration.

### F6. Construct dependence

If P1 is significant overall but the DF-hybrid advantage is absent from the
anti-hoarding constructs, the paper cannot claim a general memory-hygiene
advantage. Required reporting:

- P1 by C1 through C10, descriptive;
- P1 on the anti-hoarding aggregate C2+C3+C5+C6+C9+C10, descriptive;
- P1 on C7, descriptive;
- trap-tripped versus other-failure rates for C3, C5, C6, C9, and C10.

Claim rule:

```text
General memory-hygiene claim requires nonnegative DF-hybrid vs B5 D_obs
on the anti-hoarding aggregate and on C7.
```

If either direction is negative, the claim is limited to the constructs where
the direction holds.

### F7. New construct floor

For each new construct stratum, report the maximum S3 pass rate achieved by any
condition. If three or more new construct strata have max-condition pass rate
below 0.15, the benchmark is not discriminating on its new constructs and the
top-venue benchmark claim is killed under Section 9.5.

### F8. Author x solver contamination

If codex-authored traps are systematically easier for the codex wake agent than
for the second backbone, beyond the general wake-model difference and surviving
trap-clustered sensitivity, the paper cannot claim construction-independent
validity for those traps. The contaminated strata must be re-authored with the
separation protocol before a benchmark-primary claim.

### F9. Second wake-model transfer

If the second wake-model fold is run and its P1 direction is negative, the paper
must say the DF-hybrid-vs-B5 pattern did not transfer to the second wake model.
The primary fold remains the primary fold, but broad model-generalization
language is forbidden.

If the second model reorders the condition ladder rather than merely shifting
levels, the benchmark-primary claim is unavailable and the result is reframed as
model-dependence evidence.

### F10. Clean-start subset

The clean-start subset must be reported separately. If the primary direction
holds only in inherited-state traps and reverses or disappears in clean-start
S3 traps, the paper may not claim that the result isolates memory quality from
inherited implementation state.

### F11. Cost frontier

DF-hybrid sleep and judge cost must be reported. If DF-hybrid cost per
successful S3 task is more than 10x B5, no practical cost-effectiveness claim is
allowed, even if P1 is significant. The paper may still claim a scientific
benchmark or mechanism result if the statistics support it.

## 9. Go/no-go, null handling, and kill criteria

### 9.1 Go criteria before running the primary fold

Proceed to the primary v2 fold only if all are true:

- this preregistration has been reviewed, frozen, and hashed;
- no new v2 trap has been authored after viewing v2 performance results;
- 60 valid traps are frozen or enough pre-freeze replacement candidates exist to
  reach 60 valid traps before performance runs;
- the construct quota in Section 2.2 is satisfied;
- at least 20 traps are anti-hoarding traps;
- C1 has no more than 24 traps and no more than 40% of the final valid set;
- at least 10 new traps are `clean_start_s3 == true`;
- every new trap uses CSPRNG secret injection for non-inferable secrets;
- every new non-C1 trap passes its no-single-event or construct-specific gate;
- every new trap passes `validate_trap.py --live`;
- B0 headroom gate is satisfied on the validation/admission pass;
- 100% construct-label human audit is complete;
- at least 30% deep human audit is complete and reported;
- template cap `<=4` traps per skeleton is satisfied;
- harness pre-fixes in Section 4.5 are complete;
- run manifest, condition definitions, model configs, seeds, budgets, scorer
  hashes, and CSPRNG secret manifest hashes are frozen.

### 9.2 Abort or downgrade criteria before outcome aggregation

Abort the confirmatory fold, or downgrade it to pilot/descriptive, if any are
true:

- fewer than 60 valid traps remain and no pre-freeze replacement path can restore
  the frozen quota;
- construct quotas cannot be satisfied;
- fewer than 20 anti-hoarding traps remain;
- C1 exceeds 24 traps or 40% of the valid set;
- fewer than 10 new clean-start S3 traps remain;
- CSPRNG secret injection is violated on any admitted trap;
- B0 final S3 pass rate exceeds 0.50;
- P1 has fewer than 54 traps with at least two paired valid seeds;
- P1 cell-level validity exclusions exceed 5% for either DF-hybrid or B5;
- hidden oracle leakage is discovered;
- a condition can read another condition's memory namespace;
- any trap is edited or removed after outcome inspection;
- either required harness pre-fix in Section 4.5 is absent.

### 9.3 If the primary clustered test is null

If P1 is null under the primary clustered Holm-corrected test:

- publish the null result;
- state that the scaled fold does not establish DF-hybrid superiority over B5;
- do not promote pooled McNemar, construct slices, family slices, per-seed
  tests, transfer fold, or hygiene metrics into the headline;
- report all P1-P6 primary and secondary analyses as planned;
- retain failed and passed falsifiers in the table;
- frame any positive result as specific to the comparison that passed its
  pre-registered test.

### 9.4 If the primary clustered test is significant

If P1 is significant:

- report the exact clustered p-value and Holm-adjusted p-value;
- report pooled McNemar only as secondary;
- report whether the result survives per-seed, trap-majority, family, construct,
  clean-start, and authoring sensitivity;
- apply the falsifier constraints before writing the causal interpretation;
- do not claim typed consolidation beats verbatim replay unless P2 and P4
  support that claim under the pre-registered tests;
- do not claim cost-effectiveness if F11 fails;
- do not claim broad model generality unless the second wake-model fold supports
  that direction.

### 9.5 Kill criteria

Binding kill criteria, verbatim:

```text
>=3 new construct strata floored (<0.15 max-condition) -> arXiv measurement-study fallback; author x solver contamination -> re-author w/ separation; ladder reordering across backbones -> model-dependence analysis paper; instability at scale -> not top-venue. Never shrink back to the verbatim stratum for a lesser venue.
```

Explicitly not a kill: DF-hybrid failing to beat B5, provided the new constructs
discriminate among conditions. A null or losing system result is publishable as
a benchmark finding if the benchmark measures what it claims to measure.
